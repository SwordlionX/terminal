# Fatura Takip

`/fatura-takip` is a separate application selected from the upper-left application menu. It is not a pricing tab or a new sidebar tool. The existing Terminal pages retain their navigation and access behavior.

## Records and balances

The requested companies are seeded in order: Albayrak, Çizgi, Tempo, Aliyüce, Kalender, Elve, Rezerv, Çelebi, Zirve, Çakmakçı. Additional companies can be created in the application.

Invoices contain a company, document/invoice number, date, currency and amount. Amounts use integer hundredths of the selected currency. Company and workspace summaries group balances by currency; unrelated units are never added or converted. Existing invoices migrate additively to TRY. Currency cannot change once any usage event exists, including reversed events. CSV exports include the currency. The remaining balance is the total minus recorded usage. Every new invoice created through the application is fully used on confirmation: used equals total and remaining equals zero. The server enforces this even for an older client sending a different opening usage. One dated usage event records the automatic full use and the approving account; its date is the confirmation date rather than an invented historical usage date. Existing invoices and histories are preserved. Internal test/import helpers can still seed historical opening balances.

Usage additions and reversals are append-only events attributed to an authenticated account. Write transactions serialize balance changes, prevent overspending, and enforce idempotency for repeated usage requests. Reversing an event preserves the original event. Edits use a version check and cannot reduce an invoice below its used balance. A new invoice is rejected if its normalized document number already exists under any company. The cross-company check runs in the same write transaction as creation, preventing concurrent duplicate inserts while preserving older records. Lists are paginated, and summary totals are read within the same transaction as the displayed invoice page.

## Access and initial setup

The owner chooses a four-digit code on the initial setup screen. Administrators create each member's name and distinct four-digit code. Code changes revoke all of that account's existing sessions. Disabling a member also revokes existing sessions and trusted devices. Member accounts cannot list, create or disable accounts, add firms, view the edit audit trail, or reverse another account's usage event.

Four-digit codes intentionally have a small code space, as requested. Shared database rate limits cap failed attempts at five per address and twenty globally per thirty-minute window. A browser that has logged in successfully receives a separate trusted-device cookie (180 days, scoped to the login route, digest stored server-side). Trusted devices skip the global limit, with their own five-failure limit, so outside failures cannot lock out known devices. Codes are stored as HMAC-SHA256 digests using a server-only secret. Random 256-bit session tokens are stored only as SHA256 digests. Cookies are HttpOnly, SameSite=Strict and Secure in production with a ninety-day cookie lifetime, while the database rejects sessions idle for more than fourteen days; activity slides the window forward at most once a day. Invoice edits record the acting account with before/after values in `invoice_audit`. A QR agreement claim is stored only when the create request carries the server's 24-hour HMAC signature over the read number, date, amount and currency; otherwise it is stored as partial. Document reads are also capped per account per day (`INVOICE_DAILY_READS_PER_ACCOUNT`, default 60). Fatura Takip pages and APIs send `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff` and `Referrer-Policy: no-referrer`. All invoice APIs authenticate each request; mutation routes also check the request origin. Financial data is not stored in browser localStorage. Responses are private and not cached.

Production configuration uses the existing `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN` and `GEMINI_API_KEY`. New server-only **Secret** variables:

- `INVOICE_AUTH_SECRET`: randomly generated, at least 32 characters. Keep stable; changing it invalidates the existing account code digests.
- `INVOICE_SETUP_TOKEN`: randomly generated bootstrap token. The owner-only setup URL includes it as `?kurulum=...`. Setup is permanently refused once the first account exists. Do not place the token in source control or send it to other users.

New tables use the `invoice_` prefix in the existing Turso database. Existing customer, pricing and assistant tables are not migrated or rewritten. No file database is accepted by the production server.

## Mesnet extraction

Document recognition defaults to `gemini-3.1-flash-lite`, followed by `gemini-3.5-flash-lite`. The invoice-only `GEMINI_INVOICE_MODELS` variable can override this order; the chat application's `GEMINI_MODELS` setting does not affect it. Amounts are transcribed as printed text, with currency constrained to supported ISO codes. The application parses grouping/decimal punctuation and converts to integer hundredths; the model performs no amount arithmetic. Gemini 3.5 Flash-Lite uses minimal thinking for document extraction, and deprecated sampling parameters are omitted. Chat and research model defaults remain separate. Provider availability and project-specific quotas still apply; a larger daily quota does not guarantee lower service load.

Authenticated users can select or drop up to ten PDF, JPEG, PNG or WebP files, each up to 3 MiB. Files are processed sequentially through individual requests, with per-file progress and failure reporting. Successful results remain reviewable when another file fails; authentication failures stop the queue. Each review shows its original filename, and duplicate checks still run at save time. For FX source documents, the suggested tracking company is the issuing institution under DÜZENLEYEN YETKİLİ. These documents may describe market transactions between two outside exchange offices; the user's company need not appear. ALAN/SATAN KİŞİ/KURULUŞ remains separate reference information. Unknown issuers require manual selection rather than silently switching to the other party. The tracking amount is the FX quantity; rate and TRY counterpart are reference metadata. An unknown extracted currency remains unselected and must be explicitly chosen; it never defaults to TRY. Document text is untrusted input and has no tools or write access.

The server checks the file signature. Text-based PDFs with a recognized FX layout can use the fast path: every page must contain one complete recognized receipt, issuer must match a company, and the document number, date, currency and FX quantity must agree with structured QR evidence. The bounded browser scan supplies text only when it has covered every page; extra QR identities, unreadable pages and conflicting fields reject the fast path. It uses no Gemini calls or model budget and still requires confirmation. Unknown layouts, photos, several receipts on one page, missing QR or ambiguous evidence go to the existing Gemini visual reader. The model independently reads issuer, other party, document number, date, currency, tracking amount and warnings. Belge No takes precedence over ETTN, transaction or branch numbers. QR taxpayer numbers are not used to invent a company mapping; firm selection currently uses the printed issuer name and the company list.

PDF.js and ZXing WASM decode QR codes locally in the browser, up to twenty codes and ten pages within the time limit. Each page is first drawn at 2400 px and read in the upper-right receipt area and as a whole page; only when no data-bearing QR is found does it redraw at the detailed size (6400 px for PDFs, 3200 px for images) with the full set of overlapping crops. While one file's server request is running, the next file's local scan already starts; server requests and model calls stay sequential. Licensed pinned assets are served from the same domain, without CDN dependencies. Decoded values and bounded PDF text accompany the uploaded document; QR links are never followed. Structured QR number, quantity, currency and date are compared with visible fields, with conflicts cleared for manual entry. For multiple documents, QR evidence is associated only by the independently read document number; unidentified documents never borrow another document's QR. The bounded scan can leave some documents without QR evidence; these require visual reading and review. FX quantity times rate is checked against the TRY counterpart using integer arithmetic. A discrepancy within half the QR rate's last printed decimal plus one cent is reported as possible rounding. Rate discrepancies do not erase identity or FX fields, but prevent a full QR agreement claim; a larger discrepancy also prevents the fast path and QR-only recovery. Printed reference rates take precedence over less precise QR rates. QR agreement is a consistency check, not a digital-signature verification.

The QR scan budget starts after loading its libraries and PDF. Dependencies and the whole QR step have bounded waits; a stalled QR read falls back to Gemini review. Scanning yields through timers so a background tab does not depend on animation frames. The UI shows the current filename, queue progress and reading stage; recognition requests also have a timeout.

The extraction result fills an editable review form and never writes a record. A complete extraction opens the final confirmation directly, naming the selected company, number, date, tracking quantity, automatic full usage and zero remaining balance. Missing or conflicted fields open the correction form first. There is no opening-usage input; users review the figures and approve, or choose Düzelt to correct them. Only “Evet, onayla ve kaydet” submits the create request, with explicit confirmation required for document-source records. Editing the suggested data removes the QR agreement claim. Missing fields require correction. One PDF or image may contain up to ten independent documents, including several on the same page. Gemini returns a separate result for each document, in visible order. Multi-page continuations of one receipt stay together. Empty, oversized or explicitly incomplete batches and truncated model outputs are rejected. Each result is reviewed, corrected and confirmed separately; users can skip items and see progress and the final saved count. Existing documents are identified per result without hiding new documents elsewhere in the file. Duplicate detection runs again at save time.

If Gemini cannot finish but a consistent structured QR supplies the number, amount and currency, the app opens an explicitly labeled QR-only review. Company selection stays blank and QR status stays partial; there is no claim of independent visual agreement. Conflicting QR data or a link-only QR cannot trigger this recovery. A known incomplete batch cannot become a single QR-only result. QR-only recovery explicitly states that other documents in the file have not been read.

Each request logs a random correlation code, stage, model, provider status, finish reason and elapsed time. Invoice content, document numbers, company names, QR payloads, account data and secrets are never logged. Error responses distinguish quota, timeout, access, invalid output and service failures and include a support code.

The original uploaded file is processed in memory and is not retained as an attachment. The application saves the reviewed invoice fields; users should retain the original mesnet in their existing document archive.

One extraction request makes at most two model calls, trying a second available model only after transient provider errors or invalid structured output. Authentication, permission and malformed-request errors are not blindly retried. SDK automatic retries are disabled so each real attempt reserves its own share of the existing daily budget. It shares the assistant's existing request limit (default 20 per minute) and daily model-call budget (default 300, resetting at Istanbul midnight). Google project RPM/TPM/RPD limits are separate. Administrators can see the shared local daily counter in the Accounts screen. No Google quota reset or budget increase is performed.

## Verification

`node --test tests/invoices.test.cjs` uses isolated SQLite, with no production credentials or paid model calls. It covers leading-zero codes, hashed storage, shared login rate limits, role checks, session revocation, firm order, duplicate invoice numbers, exact balances, concurrent overspend prevention, idempotent retries, reversals, stale edits, invalid dates, Turkish amount parsing, issuer selection, rate rounding, fast-path rejection of incomplete/conflicting evidence, zero-model-call fast-path routing, and sequential multi-file failure handling.

Two supplied Albayrak PDFs were verified through the actual browser PDF.js/ZXing code and fast-path parser, returning 500,000 EUR and 123,000 EUR with Albayrak selected. A local browser test with isolated API fixtures exercised three-file upload, per-item confirmation, duplicate rejection and preservation of successful reads after one file failed. No production records were created by these checks. Customer documents and test artifacts are not committed.

The browser flow was exercised against a temporary local SQLite fixture: initial setup, login, invoice creation, usage and reversal, account creation, browser session restoration, immediate revocation, unauthorized API requests, origin rejection, application switching and mobile overflow checks. The temporary fixture is not included in the application. Actual document recognition still depends on the configured Gemini project's model availability and quota; a supplied customer PDF was checked locally for QR decoding only and was never committed or stored as a live invoice. A separate live upload of the supplied PDF confirmed that Gemini returned the expected company, document number, date and FX quantity/currency. The review form was left unconfirmed, with no live invoice record created. Synthetic fixtures cover FX counterparty matching, QR agreement/conflicts, confirmation-before-save, currency-separated balances, history currency locks, and legacy-data migration.
